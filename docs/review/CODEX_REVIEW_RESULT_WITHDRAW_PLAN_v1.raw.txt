계획 4절은 실제 스키마의 개인정보·사용자 작성 내용을 모두 다루지 않습니다.

근거:

- [schema.ts](</E:/PROJECTS/04_써보니/app/src/db/schema.ts:65>)의 `listings.title`, `description`, `check_items`와 `listing_photos` 파일은 판매자가 작성·업로드한 데이터입니다. 현재 등록 API는 제목·설명에 연락처 검사를 하지 않습니다([listings/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/listings/route.ts:59>)).
- [schema.ts](</E:/PROJECTS/04_써보니/app/src/db/schema.ts:217>)의 `orders.snapshot`, `questions`, `return_note`, `inspection`, `arrival_check`, `pack_check`에는 상품 설명·메모·사진 이름이 JSON으로 중복 저장됩니다.
- `order_photos` 파일을 지워도 `arrival_check`, `pack_check`, `inspection` 안의 사진 이름은 남습니다.
- `order_events.actor_id/data`, `disputes.detail/resolution`, `reviews.body`, `trial_reviews.answers/reason/learned/fit_for`의 보존·익명화·파기 시점이 확정되지 않았습니다.
- [feedback/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/feedback/route.ts:28>)는 `metadata.message`를 저장하지만 연락처 필터가 없습니다. 계획은 본문을 계속 남기므로 사용자가 적은 전화번호·주소 등이 남을 수 있습니다.
- [chat report route](</E:/PROJECTS/04_써보니/app/src/app/api/chats/[id]/report/route.ts:36>)의 `threadId`, `messageId`, `reportedUserId`와 [login-link route](</E:/PROJECTS/04_써보니/app/src/app/api/admin/login-link/route.ts:17>)의 `metadata.userId`는 다른 표를 통해 원래 사용자를 다시 식별할 수 있습니다.
- 상대방 알림에는 제안 답글이 복사됩니다([proposals/[id]/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/proposals/[id]/route.ts:52>)). 계획은 `trial_proposals.seller_reply`만 비우고 복사된 알림 본문은 처리하지 않습니다.
- `seller_profiles`, `buyer_profiles`, `xp_awards`, `reviews`, `trial_reviews`를 원래 사용자 ID와 연결한 채 기한 없이 남기면서도 보존 목적과 종료 시점이 없습니다.
- `withdrawals`가 원래 사용자 ID와 카카오 회원번호를 언제 지우는지도 없습니다.

수정안:

1. 모든 표·JSON 키·파일을 대상으로 `즉시 삭제 / 법정 분리 보관 / 익명화 후 유지 / 보존 근거 없음` 4가지로 분류하십시오.
2. `orders`의 각 텍스트·JSON 키와 `market_validation_events.metadata`의 이벤트별 키를 개별 행으로 적으십시오.
3. 상대 알림에 복사된 닉네임·제안 답글·상품 제목도 포함하십시오.
4. `withdrawals.kakao_id`, 원래 사용자 ID, 재시도 오류 기록의 최종 삭제 조건을 확정하십시오.

### 막는 문제 2 — 법령의 보존 범위와 분리·파기 설계가 충분하지 않음

5년·3년이라는 기간 자체는 맞지만, 계획의 적용 범위는 법 조문보다 넓거나 일부 빠졌습니다.

- 현행 시행령 제6조에는 표시·광고 기록 6개월, 계약·청약철회 및 대금결제·공급 기록 5년, 불만·분쟁처리 기록 3년이 규정되어 있습니다. 계획은 6개월 기록을 누락했고, 모든 채팅과 사진을 일괄적으로 3년짜리 분쟁 기록으로 간주했습니다. 일반 채팅 전체가 자동으로 분쟁처리 기록이 된다는 문구는 원문에 없습니다. [전자상거래법 시행령 제6조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lspttninfSeq=63460)
- 개인정보보호법 제21조는 불필요한 개인정보의 지체 없는 파기, 복구·재생 방지, 법률상 보존 자료의 분리 저장·관리를 요구합니다. [개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334901)
- 같은 운영 SQLite DB에 `retained_records` 표만 추가하는 것으로는 별도 접근 권한·일반 조회 차단·키 관리가 정의되지 않아 “분리 관리”가 성립하는지 판정할 수 없습니다.
- 현재 DB는 WAL 모드이고([client.ts](</E:/PROJECTS/04_써보니/app/src/db/client.ts:5>)), `secure_delete`, WAL 체크포인트, 백업 만료 정책이 없습니다. 행 삭제만으로 “복구·재생되지 않게 파기”했다고 주장할 수 없습니다.
- 파일 삭제도 현재 `unlink` 오류를 삼키는 경로가 있습니다([photos.ts](</E:/PROJECTS/04_써보니/app/src/lib/photos.ts:52>)).

수정안:

- 법정 기록 종류별로 6개월·5년·3년 대상 필드를 정확히 매핑하십시오.
- 일반 채팅과 사진은 실제 분쟁에 사용된 기록과 그 밖의 대화를 분리해 보존 근거를 정하십시오.
- 분리 보관 자료의 접근 주체, 일반 화면·관리자 CSV 제외, 암호화 키, 키 교체, 만료 파기, WAL·백업·파일 파기 절차를 계획에 넣으십시오.
- 이는 법률 자격 판정이 아니라 현재 계획이 인용한 법 조문과 구현 주장의 일치 여부에 대한 검수입니다.

### 막는 문제 3 — 탈퇴와 동시에 이미 시작된 쓰기 요청을 막지 못함

계획은 주문·새 제안·새 채팅방 세 곳만 트랜잭션 안에서 다시 확인합니다. 그러나 세션 확인 뒤 탈퇴가 먼저 커밋되면 다른 API가 탈퇴자의 데이터를 다시 만들 수 있습니다.

실제 예:

- 찜 API는 사용자 상태를 트랜잭션 안에서 다시 확인하지 않고 찜과 이벤트를 삽입합니다([wishlists/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/wishlists/route.ts:17>)).
- 수요 등록도 같은 구조입니다([demand-intents/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/demand-intents/route.ts:33>)).
- 정산 계좌 PUT도 세션 확인 후 바로 다시 저장할 수 있습니다([seller-account/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/seller-account/route.ts:29>)).
- 푸시 구독도 탈퇴 처리에서 지운 뒤 진행 중 요청이 다시 삽입할 수 있습니다([push/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/push/route.ts:17>)).
- 채팅 메시지 POST는 상대뿐 아니라 발신자 상태도 트랜잭션 안에서 다시 확인해야 합니다([chats/[id]/route.ts](</E:/PROJECTS/04_써보니/app/src/app/api/chats/[id]/route.ts:31>)).

수정안:

- 개인정보 또는 사용자 소유 데이터를 쓰는 모든 API에 공통 `ACTIVE` 쓰기 장벽을 적용하십시오.
- 단순 사전 조회가 아니라 각 쓰기 트랜잭션 안에서 발신자·상대·소유자의 상태를 다시 검사해야 합니다.
- 주문·제안·채팅방 외에 찜, 수요, 상품·사진, 정산 계좌, 푸시, 알림 설정, 피드백, 후기, 분쟁, 채팅 메시지를 포함한 전체 쓰기 API 목록을 계획에 추가하십시오.
- 탈퇴 트랜잭션과 각 API를 의도적으로 교차시키는 경쟁 시험이 필요합니다.

### 막는 문제 4 — 카카오 연결 끊기와 즉시 재가입이 충돌함

계획은 운영 서버에 어드민 키가 없는데도 키가 없으면 `SKIPPED_NO_KEY`로 끝냅니다. 현재 코드는 로그인 때 받은 액세스 토큰을 사용자 정보 조회 후 보관하지 않습니다([kakao.ts](</E:/PROJECTS/04_써보니/app/src/lib/kakao.ts:99>)). 공식 API상 연결 끊기는 사용자 액세스 토큰 또는 서비스 앱 어드민 키가 필요합니다. [카카오 로그인 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api)

더 큰 문제는 다음 순서입니다.

1. 기존 계정 탈퇴 후 로컬 `social_accounts` 삭제
2. 원격 연결 끊기 실패로 `PENDING`
3. 같은 카카오 ID로 새 로컬 계정 생성
4. 예전 탈퇴 작업 재시도가 같은 카카오 ID의 원격 연결을 끊음

이 경우 새 계정의 카카오 연결까지 뒤늦게 끊기며 로컬 연결 상태와 카카오 상태가 달라집니다.

수정안:

- 운영 기능 활성화 전 어드민 키를 필수 조건으로 하거나, 탈퇴 요청 시점에 가진 액세스 토큰으로 즉시 끊는 설계를 마련하십시오.
- 키가 없을 때는 성공 상태로 건너뛰지 말고 기능을 열지 않거나 명확한 `BLOCKED_NO_KEY` 상태로 남겨야 합니다.
- 같은 카카오 ID의 재가입은 이전 unlink가 끝날 때까지 막거나, 사용자의 새 로그인 시 예전 재시도를 원자적으로 취소하는 정책을 확정하십시오.
- 상태를 `PENDING / SUCCEEDED / RETRYABLE / FAILED / CANCELLED_BY_RELINK`처럼 구분하고 시험하십시오.

### 막는 문제 5 — 시험 사례로 합격 기준과 주요 정책을 모두 판정할 수 없음

일부러 틀린 입력 시험은 있습니다. 사례 13의 확인 문구 오류 400, 남의 ID 무시, 예약 닉네임 거절은 적절합니다.

하지만 다음 시험이 빠졌습니다.

- 카카오 unlink 성공·500 재시도·최대 횟수·키 없음·재가입 충돌
- `WITHDRAW_ENABLED` 비활성 API 503 및 버튼 숨김
- 1분 3회 제한과 서버 재시작·복수 프로세스에서도 같은 제한
- 트랜잭션 중간 고의 실패 후 DB 변경 0건
- 파일 삭제 실패 후 재시도와 최종 파일 부재
- 주문·분쟁·채팅·광고 기록별 정확한 파기 시각
- seller account, social account, login link, push, notification prefs 등 즉시 삭제 대상 전수 확인
- `market_validation_events.metadata`와 상대 알림 복사본 정리
- 탈퇴와 찜·수요·계좌·사진·푸시·메시지 요청 경쟁
- WAL·백업·파일을 포함한 복구 불가 파기 증거
- 보존 자료가 일반 화면·내보내기·관리자 통계에서 노출되지 않는지

수정안:

- 13절 합격 기준에 위 항목을 각각 추가하고, 모든 기준을 시험 번호에 연결하십시오.
- 성공 사례만이 아니라 오류 주입, 기한 경계 직전·직후, 동시 요청의 반대 실행 순서까지 넣으십시오.

## 3. 개발하면서 고쳐야 할 문제

### 3-1. 설계–코드 대조표의 읽기·쓰기 대상이 일부 부정확함

- 계획 5절의 `notifyTx` 행은 “쓰는 표 없음”이지만 실제 함수는 `notifications`를 삽입·갱신합니다([notify.ts](</E:/PROJECTS/04_써보니/app/src/lib/notify.ts:40>)).
- `photoPath`는 파일을 지우는 함수가 아니라 경로만 계산합니다([photos.ts](</E:/PROJECTS/04_써보니/app/src/lib/photos.ts:24>)).
- 자동 파기 행에는 `order_events`, `market_validation_events`, 상대방 `notifications`, JSON 안 사진 이름, 실제 파일시스템 쓰기가 빠졌습니다.

수정안: DB 표뿐 아니라 파일 읽기·쓰기까지 대조표에 적고, 실제 삭제 함수와 재시도 함수를 별도로 명시하십시오.

### 3-2. 제안 본문 삭제 범위가 서로 다름

Q6-4는 제안 한마디·답글을 바로 모두 비운다고 했지만 4절은 `PENDING·ACCEPTED` 상태 변경과 함께 적혀 있어 `DECLINED·CANCELLED·EXPIRED` 기록도 비우는지 불명확합니다.

수정안: 상태와 관계없이 탈퇴자가 작성한 `message` 또는 `seller_reply`를 모두 비우고, 상대 알림에 복사된 답글도 함께 처리한다고 명시하십시오.

### 3-3. 보존 암호화 키 교체 계획이 구현 범위에 없음

기존 암호화 키는 `SESSION_SECRET`에서 파생됩니다([crypto-box.ts](</E:/PROJECTS/04_써보니/app/src/lib/crypto-box.ts:5>)). 계획 17절은 키를 바꿀 때 재암호화한다고 적었지만 대상 함수·키 버전·중단 복구·시험이 없습니다.

수정안: 암호문에 키 버전을 두고, 이전 키로 읽고 새 키로 다시 저장하는 절차와 실패 시 원복을 계획에 추가하십시오.

### 3-4. 요청 제한 저장 방식이 정해지지 않음

탈퇴 1분 3회 제한이 메모리 기반이면 재시작·복수 서버에서 우회됩니다.

수정안: DB 기반 시도 기록 또는 기존 영속 제한 방식을 지정하고 경계 시각과 정리 주기를 시험하십시오.

### 3-5. 검수 기준 작업 상태 설명이 실제 Git 상태와 다름

브랜치 `gate0/market-ui`와 HEAD `8eaffa3`은 일치합니다. 그러나 “커밋되지 않은 변경 2건”과 달리 현재 `git status`에는 파일 단위 항목이 166개 있으며, 추적 파일에도 `AGENTS.md`, `CLAUDE.md`, 운영자 화면, 시험 코드와 다수 이미지 변경이 있습니다.

수정안: 다음 계획서에는 실제 `git status` 기준으로 검수 제외 파일을 정확히 열거하고, 개발 시작 전에 탈퇴 기능이 덮어쓰면 안 되는 변경을 보호 목록으로 고정하십시오.

## 4. 작은 문제

- 요청서 번호 `REQ-써보니-...`는 공통 규칙의 `REQ-<프로젝트 2자리>-...` 형식과 다릅니다. 이번 요청은 제목·시각·대상이 유일해 검수를 진행했지만 다음 판부터 `REQ-04-YYYYMMDD-HHMMSS` 형식이 맞습니다.
- 자체 검토 확인서는 “다른 보조 검토자”라고만 적어 작성 주체와 실행 근거가 추적되지 않습니다. 계획 판정 자체를 막지는 않지만 검토자 또는 세션 근거를 남기는 편이 좋습니다.
