- T10은 미설정·`0`·`false` 모두 GET/POST 503과 버튼 없음, 정확히 `1`일 때만 사용 가능함을 확인해야 합니다.

### 막는 문제 2 — P1의 7일 거래 기준이 실제 분쟁 가능 조건과 다름  
구분: **ⓒ 이번 검수에서 처음 발견**

계획은 모든 최종 상태를 “완료 뒤 7일 이내”로 막고 실제 분쟁 기간과 같다고 설명합니다. 실제 코드는 `CANCELLED` 거래의 분쟁을 기간과 관계없이 금지하고, 나머지 최종 거래는 `completed_at`이 있을 때만 7일을 계산합니다.

근거:

- 계획 P1: [WITHDRAW_PLAN_v5.md](</E:/PROJECTS/04_써보니/docs/review/WITHDRAW_PLAN_v5.md:30>)
- `CANCELLED`는 즉시 분쟁 불가: [orders.ts](</E:/PROJECTS/04_써보니/app/src/lib/orders.ts:594>)
- 7일 검사는 `completedAt`이 있는 최종 거래만 적용: [orders.ts](</E:/PROJECTS/04_써보니/app/src/lib/orders.ts:595>)

수정안:

- 권장 기준은 다음과 같습니다.
  - 비최종 거래: 탈퇴 차단
  - OPEN 분쟁: 탈퇴 차단
  - `PURCHASED`·`RETURNED`: `completed_at` 없음 또는 완료 후 168시간 이하이면 차단
  - `CANCELLED`: OPEN 분쟁이 없다면 7일 차단에서 제외
- 모든 최종 거래를 7일간 막겠다면 “현재 분쟁 정책과 동일”이라는 설명을 삭제하고 별도 운영 정책 제안값으로 표시하십시오.
- T2는 6일·8일 대신 정확히 168시간 직전·정확히 168시간·1초 이후, `completed_at=NULL`, `CANCELLED`를 시험해야 합니다.

### 막는 문제 3 — 차단 실패·재요청·중간 오류의 원자성 계약이 불명확함  
구분: **ⓐ 1차 시험 부족 문제가 아직 안 풀림**

P2는 트랜잭션 첫 줄에서 사용자를 `WITHDRAWN`으로 바꾼다고 하면서 P1은 트랜잭션 안에서 거래를 다시 확인한다고 합니다. 차단 거래 발견 시 예외로 전체 롤백할지, 409 결과를 반환하며 앞선 상태 변경을 커밋할지 명시되지 않았습니다.

또한 일반 재요청은 `getCurrentUserId()`가 이미 탈퇴한 사용자를 거부하므로 항상 `{already:true}`가 되지 않습니다.

근거:

- P1·P2 순서: [WITHDRAW_PLAN_v5.md](</E:/PROJECTS/04_써보니/docs/review/WITHDRAW_PLAN_v5.md:30>)
- 기존 인증은 ACTIVE가 아니면 사용자 ID를 반환하지 않음: [session.ts](</E:/PROJECTS/04_써보니/app/src/lib/session.ts:53>)
- T5는 두 번째 요청 결과를 항상 `already`로 가정: [WITHDRAW_PLAN_v5.md](</E:/PROJECTS/04_써보니/docs/review/WITHDRAW_PLAN_v5.md:91>)
